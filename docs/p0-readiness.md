## 3. 七版本实例与演练

七个精确版本均从官方 docker.gitea.com/gitea 镜像取得，固定摘要见 [images.lock.json](../tests/integration/images.lock.json)。Compose 中已使用同一摘要固定镜像，每个实例有独立命名卷和固定 loopback 端口。实际观察到的容器架构为 Linux arm64。

| 精确版本 | 端口 | 版本入口核对 | 初始化／重置轮数 | 资源与权限核对 |
| --- | --- | --- | --- | --- |

| 1.23.8 | 32308 | 与目标相同 | 2 | 通过 |
| 1.24.7 | 32407 | 与目标相同 | 2 | 通过 |
| 1.25.5 | 32505 | 与目标相同 | 2 | 通过 |
| 1.26.4 | 32604 | 与目标相同 | 2 | 通过 |
| 1.27.3 | 32703 | 与目标相同 | 2 | 通过 |
| 28.3.0 | 32830 | 与目标相同 | 2 | 通过 |

每轮实际核对三类账号身份、owner 私有仓库访问、受限账号拒绝访问、3 个 Issue 在 limit=2 下的两页结果且不混 PR、两个 PR 读取、一个草稿 Release 及单个附件，并核对 clone URL 对应本机端口。第二轮删除固定测试仓库后完整重建，账号和其他项目不被删除。锁定摘要的最终 Compose 配置再执行现有数据只读核对。

组织／团队场景设计预留 sotea-p0-org 与 p0-reviewers；本阶段的最小演练使用个人私有仓库，团队审查与跨组织场景在 P4 对应任务准备时补充，不将尚未创建的组织写为已验证资源。

正式业务命令尚未实现，因此上述结果只证明镜像可取得、版本可检测和测试场景可初始化。负责人旧版适配、审查／合并、业务写入故障恢复和 MCP 代表性流程仍按 P2 至 P7 验收。

本轮结束时已停止全部七个 P0 服务，容器正常退出，镜像与命名卷／测试数据保留。P1 可按环境说明重新 up 后使用现有数据，不需要重复下载或重新初始化；未操作其他 Docker 项目。

## 4. 隔离与故障设施

| 设施 | 已执行行为 | 结果 |
| --- | --- | --- |
| Git helper | 临时仓库、独立系统／全局配置，fill 两次及 approve／reject。 | get／get／store／erase 顺序正确，useHttpPath 开关行为符合预期，日志无合成密码。 |
| HTTP 状态 | /ok 和 /status/403。 | 成功状态和失败状态可区分。 |
| HTTP 超时 | 延迟响应，客户端更短超时。 | 超时可重复触发。 |
| 请求中断 | POST 后主动断连，通过 /events 查询次数。 | 只观察到一次 POST；后续可用于发现意外重放。 |
| TLS／私有 CA | 先用默认信任连接，再显式提供测试 CA。 | 未知 CA 被拒绝，显式 CA 后连接成功；无关闭证书校验。 |
| 资源清理 | helper 临时目录自动清理，HTTP／TLS 监听和线程退出。 | 不保留额外本机监听，不访问真实 helper 或系统密钥库。 |

首次 TLS 演练发现 Python 3.13 的严格验证会拒绝缺少 CA keyUsage 的证书；已补齐 critical basicConstraints／keyUsage 及叶证书用途扩展并重新通过。该问题属于夹具修复，不是通过降低 TLS 校验规避。
