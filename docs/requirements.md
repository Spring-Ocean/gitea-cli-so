# sotea 需求文档

> 状态：首版功能范围已确认；实现与验收未完成
>
> 更新日期：2026-11-06

## 1. 背景与目标

团队使用自部署 Gitea，希望有一个统一的命令行工具，在本地 Git 仓库上下文中完成 Git 和 Gitea 操作，并让支持 MCP 的客户端使用相同的能力。

产品目标：

- 支持团队现有的 Git 仓库、Git 配置和凭证使用方式。
- 提供 Gitea API 的通用调用能力，覆盖实例支持的全部 API，并为常用操作提供易用的命令。
- 在 CLI 中内置本地 stdio MCP 服务，使 MCP 客户端能够访问相关能力。
- 兼顾交互式使用、脚本调用和自动化集成。

## 2. 范围与使用对象

使用对象包括团队开发者、维护人员、自动化脚本和通过 MCP 接入的客户端。首版面向一个或多个自部署 Gitea 实例；其他 Git 平台不纳入首版兼容承诺。

使用 Go 1.27.3 实现，为 macOS 和 Windows 分发预编译程序。首版纳入当前 TDD 的业务命令、交互补全和无参数持续菜单；MCP 工具方案另见 mcp-design.md。七个目标 Gitea 版本均必须支持，架构和最低运行环境等交付条件仍需验证。

## 3. 功能需求

### 3.1 Git 集成

1. 支持执行 Git 命令，并尽量保留 Git 原有的参数、输出、退出码和交互行为。首版提供 sotea git -- <args> 透传；作为 Git 子命令不纳入首版要求。
2. 能识别当前工作目录及其上级目录中的 Git 仓库，读取仓库路径、分支、remote 等上下文。非仓库目录、多个 remote、无 remote 等情况应有明确提示或允许显式指定。
3. 支持利用现有 Git 配置及凭证体系访问仓库。优先复用用户已有的 Git 能力；不得假设所有凭证都可直接读取为明文，且不得在日志或输出中泄露凭证。
4. 支持使用 Git 的能力完成仓库操作。首版调用本机 Git 可执行程序，复用其配置、凭证与 SSH 能力；纯 API 操作不要求安装 Git。
5. 允许用户显式指定仓库或 remote，明确其与自动推断结果的优先级；匹配、歧义与优先级按 [CLI 契约](cli-contract.md)执行。

### 3.2 Gitea API 和业务命令

1. 提供通用 API 调用入口，允许用户指定实例、HTTP 方法、API 路径、查询参数、请求头和请求体，获取响应及错误信息。
2. 目标是可调用目标 Gitea 实例支持的全部 API，不因没有专用业务命令而受限。实际可执行范围仍由实例版本、开放的接口、账号权限和服务器配置决定；不承诺绕过这些限制。
3. 为日常开发操作提供有语义的命令，首版重点为 Issue、Pull Request（PR）、Release，以及支撑这些流程的仓库、分支、标签和提交状态。确认清单见第 3.2.1 节；命令、选择与确认规则见 TDD 及 CLI 契约。首版同时保留通用 API 调用能力。
4. 支持从本地仓库上下文推断目标实例及仓库，也支持通过参数显式指定；自动推断失败时应给出可操作的提示。
5. 对分页、结构化输出和 API 错误提供适合脚本使用的处理方式。默认按页读取，批量目标及结果遵循 CLI 契约；大文件流式处理，失败和取消不能误报为全部成功。
6. 需要兼容多个 Gitea API 版本。当前已知稳定版支持范围为：`28.3.0`、`1.27.3`、`1.26.4`、`1.25.5`、`1.24.7`、`1.23.8`、`1.22.6`。
7. API 兼容性应以 Gitea 实例实际版本为准：通用 API 调用入口不应因为没有对应的专用业务命令而失效；首版专用命令的共同功能必须在七个目标版本工作；新增版本的专有字段不自动纳入共同功能。原生端点缺失时须完成经验证的客户端适配，不能仅返回“不支持”便视为达标。
8. 对跨版本差异，应优先在客户端适配请求和响应模型；无法兼容时返回可识别的版本或接口错误，不得静默改变用户请求的含义。

首版 API 兼容性验证目标如下：

| Gitea 版本 | 首版要求 | 验证方式 |
| --- | --- | --- |
| `28.3.0` | 必须支持 | 建立对应测试实例，执行通用 API、仓库、Issue、Pull Request、Release 和 MCP 代表性回归。 |
| `1.27.3` | 必须支持 | 同上。 |
| `1.26.4` | 必须支持 | 同上。 |
| `1.25.5` | 必须支持 | 同上。 |
| `1.24.7` | 必须支持 | 同上。 |
| `1.23.8` | 必须支持 | 同上。 |
| `1.22.6` | 必须支持 | 同上。 |

以上是首版明确要求验证的精确版本。未列出的补丁版本或其他版本线是否纳入兼容承诺，仍待确认；如需扩大范围，应在兼容矩阵和测试结果中记录依据。版本识别失败时通用 API 仍允许调用；专用命令按已建立的适配证据处理，不能通过猜测写入探测版本。七版本中的任何首版必需功能未适配或未通过真实实例验收，均阻断正式发布。

#### 3.2.1 首版开发常用操作确认清单

以下是已确认首版范围，与 TDD 第 4.2 至 4.5 节的所有业务命令逐项对应；交互式选择也纳入，具体多选与确认按 cli-contract.md 执行。参考 [Gitea 28.3.0 API 文档](https://docs.gitea.com/api/)及其 [OpenAPI 定义](https://docs.gitea.com/openapi3-28.json)。文档展示接口不代表各目标版本都已验证兼容。

| 领域 | 首版支持的常用操作 | 典型需求 |
| --- | --- | --- |
| Issue | 列表、筛选、查看、创建、编辑、关闭和重新打开；查看和添加评论；管理负责人和标签。 | 查询待办、记录问题并推进处理。 |
| PR | 列表、筛选、查看、创建、编辑、关闭和重新打开；查看变更文件及提交；查看和添加普通评论。 | 提交代码、讨论变更和追踪合并请求。 |
| PR 审查与合并 | 查看审查记录、请求审查、提交审查意见及合并。 | 支持代码评审和按仓库策略合并。单 PR 审查与合并，按 CLI 契约显示目标和选项并确认。 |
| Release | 列表、按版本标签查看、创建和编辑；支持草稿、预发布标识；列出和上传附件。 | 发布版本说明与交付产物；删除及附件下载可走通用 API，首版不增加对应专用命令。 |
| 仓库与代码上下文 | 查看当前或指定仓库、列出分支和标签、查看提交及其状态。 | 确认目标仓库、源分支、版本标签和检查状态。 |
| Issue 关联资源 | 列出仓库标签和里程碑；设置 Issue 的标签和里程碑。 | 按团队流程分类和规划工作。 |

PR 普通评论与代码行审查评论分开；当前表中审查提交是 PR 级审查，代码行评论、回复和解决的专用命令不纳入首版。Release 默认创建草稿，缺少标签时必须明确目标提交，附件同名报冲突；创建和恢复行为见 CLI 契约，并须逐版本测试。列表的筛选、分页及结构化输出覆盖上表场景。

Actions 工作流管理、组织和站点管理、Webhook 等暂不列为首版专用命令承诺，仍可通过通用 API 调用；是否增加专用命令后续讨论。

### 3.3 认证与配置

1. 默认从启动目录发现 Git 仓库和 remote，识别并验证目标 Gitea；HTTPS 推断和 SSH 到 HTTP 地址映射按 CLI 契约处理，不以域名或版本字符串作为唯一平台证据。
2. 登录体验复用 Git credential helper、系统凭证管理器及 Git 已有交互习惯，提供 auth login、status、switch、refresh、logout。通过 GET /api/v1/user 验证实际远端身份；Git user.name、user.email 不是远端认证账号。
3. HTTPS Git 凭证经 API 验证可复用；SSH 认证不自动产生 API token，无法复用时安全输入独立 token。API 认证与 Git 传输凭证分别管理，不强制二者使用同一身份。
   HTTPS 凭证按协议、主机及显式端口、已知用户名和 Git 配置决定的路径上下文查询；默认不按仓库路径区分 helper 凭证，尊重 credential.useHttpPath，不自动扩大到父域或其他子域。sotea 自有 API 引用则绑定完整实例根地址与已验证账号，同实例多个仓库可以复用；详见 CLI 契约第 4.3 节。
4. 保存多个实例和账号，按显式参数、环境变量及保存的活动账号选择。切换 sotea 账号不修改 Git commit 作者或 SSH 设置。
5. 401 标记失效并提供重新登录路径；403 表示权限不足，不自动删除凭证。刷新凭证须验证后替换，退出默认移除 sotea 自有认证记录并持久化退出抑制标记，防止下次通过 Git helper 隐式重登；清理共享 Git helper 凭证须明确选择和确认。环境 token 由外部管理，必须提示移除变量及重启相关 MCP 进程，不能声称已经删除。
6. 显式要求账号 A，API 验证为 B 时默认报 AUTH_IDENTITY_MISMATCH，不继续业务请求或写入；交互式登录必须明确同意切换身份，--yes、脚本和 MCP 不自动替换。helper 的占位用户名不等于 API 账号。
6. 非敏感配置为带版本的 JSON，密钥使用系统安全存储或运行时环境注入，不静默保存明文；支持私有 CA，默认验证 TLS。优先级、路径和并发更新规则见 [cli-contract.md](cli-contract.md)。

### 3.4 MCP

1. CLI 内置本地 stdio MCP 服务，由客户端启动并管理，退出不依赖另一个终端菜单进程。
2. 工具覆盖上下文、身份状态、仓库、Issue、PR、Release 和开发上下文；固定工具清单及 Schema 方案见 [mcp-design.md](mcp-design.md)。
3. 默认只读；用户配置 --allow-write 后提供准备、提交和状态查询工具。写操作先展示具体目标及修改，再按客户端审批机制提交；服务端无法凭工具调用证明人工已批准，此限制必须明确。
4. 通用 API 工具通过 --allow-raw-api 单独启用，写请求同时需 --allow-write；本地文件及固定 Git 查询限定在明确授权的工作目录。首版不暴露任意 shell 和任意 Git 写命令。
5. CLI 与 MCP 共享应用服务及多版本适配；MCP 不弹终端选择器、不使用协议 stdin 登录，工具需显式参数或确定的工作区上下文。
6. stdout 仅承载协议；支持取消、结果未知、部分失败、重复提交保护、EOF 清理及脱敏日志。首版不包含远程 HTTP 服务或共享后台守护进程。

### 3.5 命令行体验

- 程序帮助、操作提示、错误、诊断、交互菜单、表头及 MCP 用户可见摘要统一使用英文；远端用户内容与原始 Git／API 输出保持原文。开发文档继续使用中文。

- 可交互终端执行无参数 sotea 进入持续菜单，在当前目录识别仓库并提供当前 TDD 的全部首版操作，完成后可继续操作或退出；非仓库目录允许选择／输入实例与仓库。
- 子命令缺少必需目标时查询候选并选择；缺少必要内容时提示输入，参数齐全时保留直接执行方式。
- Issue 和 PR 的关闭、重开支持 1–100 个目标；编辑、评论、审查、合并及 Release 操作为单资源目标。负责人、标签和审查者等字段可多选，见 CLI 契约。
- 所有业务写操作都要预览并确认，包括直接传编号；--yes 表示明确跳过本次确认，不代表自动选择目标。通用 API 非读取方法也遵循确认规则；Git 透传沿用 Git 自身规则。
- --no-interactive、--json、CI、管道或无终端时不得等待输入；写入必须参数齐全且带 --yes，否则报错。无参数且无终端时显示帮助退出。
- 普通输出支持表格、颜色和加粗，兼容 macOS Terminal、iTerm2 和目标 Windows PowerShell 宿主；JSON、原始 API 响应、Git 与 MCP 各自遵循输出契约。
- 搜索、分页、多选、取消、状态变化和部分失败必须有明确反馈；没有目标或提交前取消时不写入。不得将第一页当成全部结果或默认选择第一项。
- 稳定的结果 Schema、逐项结果和退出码见 [cli-contract.md](cli-contract.md)，不能将部分完成和结果未知称为全部成功。

## 4. 非功能需求

- **安全性**：保护凭证，默认采用安全连接配置；避免无意输出敏感信息。
- **兼容性**：七个指定 Gitea 版本必须支持；操作系统、CPU 架构、终端宿主及最低 Git 版本在发布前完成支持矩阵与实际验证。
- **可靠性**：对网络异常、认证失败、权限不足、接口不兼容和非 Git 目录提供明确反馈，不将失败误报为成功。
- **可维护性**：CLI、API 和 MCP 共享核心能力，避免同一操作出现不一致行为。
- **可测试性**：支持自动化测试，并在团队目标 Gitea 实例或可控测试环境验证关键流程。
- **分发**：使用 Go 1.27.3 实现，为 macOS 和 Windows 提供预编译程序；具体方案见第 8 章。
- **开源许可**：项目采用 MIT License，发布时附带许可证。当前不计划注册商标。

| 写入与批量 | 直接传编号也确认；非交互用 --yes；目标和多值范围按 CLI 契约固定。 |
| MCP | 本地 stdio，默认只读，显式启用写入，准备后提交；工具清单见 MCP 设计。 |
| 多版本 | 七个指定版本必须支持全部首版共同功能；适配不完整或未实测不得宣布正式支持。 |
| 工程 | Go 1.27.3，Cobra，系统 Git，macOS / Windows 预编译；样式及交互库按设计实施时锁定。 |

P0 已完成七版本隔离实例、最小数据重建及现有环境盘点，证据见 [p0-readiness.md](p0-readiness.md)。待落实的是后续交付与验收条件：正式 CPU 架构和最低系统／Git 版本、Windows 宿主及设备、发布地址、签名条件、依赖版本，以及全部客户端／业务的真实验收。第 8 章的建议需在发布前形成明确支持矩阵；不能将 P0 基础设施通过写成这些项目已经通过。

## 7. 实现语言

### 7.1 已确定的需求

- 项目使用 **Go** 实现，开发和正式构建使用 **Go 1.27.3**。
- Go 版本应在项目和构建流程中明确记录，开发者和 CI 使用一致的工具链，避免构建结果因版本差异而不可预测。
- 后续如需更新 Go 版本，应先评估兼容性和安全修复，并通过测试后更新项目约定；不自动将版本上限或升级策略视为已确定需求。
- CLI、Gitea API 和 MCP 服务应共享核心能力。依赖库及具体实现方式留待技术设计确定。

Go 工具链版本 `1.27.3` 与 Gitea 服务端版本是两个独立的版本维度：前者约束本项目的构建环境，后者约束 API 请求、响应和权限行为。两者不能混用或互相替代。

Go 官方发布历史中列有 [Go 1.27.3](https://go.dev/doc/devel/release)。采用 Go 不意味着已经确定 Git 的实现方式：如果最终选择调用系统 Git，用户仍需安装 Git。

### 7.2 验收

在约定的开发环境和 CI 中，使用 Go 1.27.3 完成构建和项目测试；发布产物记录工具版本及对应构建信息。构建细节在技术设计中确定。

## 8. 分发与平台支持

### 8.1 已确定的需求

- 为 **macOS 和 Windows** 提供预编译程序，用户运行 CLI 无需安装 Go。
- CLI 和本地 stdio MCP 服务随同一套发布产物提供，用户不需要另外安装 MCP 服务。
- Windows 正式支持向下覆盖 Windows 10，首版最低基线为 Windows 10 22H2 amd64，同时支持 Windows 11；两者均须完成真实运行验收。
- macOS 最低版本、其他架构、安装方式和更新方式仍按下面的首版建议评估。

### 8.2 支持平台建议

| 平台 | 架构 | 首版建议 | 验证要求 |
| --- | --- | --- | --- |
| macOS | arm64（Apple Silicon） | 支持 | 在相应环境验证 CLI、Git 集成和 MCP 启动。 |
| macOS | amd64（Intel） | 支持 | 在相应环境验证同样的关键流程。 |
| Windows | amd64（Intel / AMD 64 位） | 已确定覆盖 Windows 10 22H2 和 Windows 11 | 两个系统分别验证关键流程、路径、终端及凭证行为，不能相互代替。 |
| Windows | arm64 | 建议支持原生构建；团队没有设备或 CI 环境时，先确认测试条件再承诺正式支持。 | 在 Windows ARM 环境验证关键流程；仅成功交叉编译不足以证明运行兼容。 |
| Linux、Windows 32 位及其他平台 | 待讨论 | 首版暂不承诺；如团队 CI 或服务器需要 Linux，应调整范围。 | 确定范围后补充构建和运行测试。 |

各平台的最低操作系统版本应在核对团队设备、Go 1.27.3 的支持范围以及第三方依赖后确定，不能仅以构建成功作为兼容承诺。Go 的 [平台支持策略](https://go.dev/wiki/PortingPolicy)和[目标平台列表](https://go.dev/doc/install/source#environment)可作为评估依据。

Windows 最低支持已确定为 Windows 10 22H2 amd64，Windows 11 25H2 作为较新系统的验收基线；Windows 10 必须覆盖自带 PowerShell 5.1 和 Windows Terminal，不强制用户升级系统或安装 PowerShell 7。Git 2.43 已在 P3 确定为集成功能基线，2.43.7 隔离样本通过 core／helper 验证；macOS 仍建议 15，Windows 11 推荐 PowerShell 7.6 LTS 与 Windows Terminal；macOS 13／14 仍仅列可选兼容环境。依据、终端要求及验收矩阵见 [platform-support.md](platform-support.md)。除已确定的 Windows 范围和 Git 功能基线外，其余最低版本仍为提案；完整目标矩阵尚未完成实际运行验证，不改变七个 Gitea 服务端版本必须支持的要求。

### 8.3 安装与升级建议

1. **基础交付**：每个版本提供按系统和架构区分的压缩包，包含 CLI 程序、版本及安装说明。建议 macOS 使用 tar.gz，Windows 使用 zip；程序名称为 sotea，压缩包命名规则在发布流水线中固定。
2. **安装**：下载并解压后，将程序放到 PATH 中的目录；文档分别提供 macOS 和 Windows 示例及卸载步骤。无需管理员权限的安装路径优先，但以团队环境为准。
3. **发布位置**：建议使用团队自部署 Gitea 的版本发布页面集中提供产物、变更说明和校验值；访问权限和实际地址待确认。
4. **升级**：首版建议通过下载新版本替换程序，保留已有配置；提供版本查看能力和升级说明。自动更新、更新检查及包管理器接入作为后续选项，不默认自动联网或覆盖程序。
5. **可选渠道**：后续根据团队使用情况评估 Homebrew、WinGet 或 npm 包装分发；它们与 Go 的实现语言无关，首版暂不作为已确定要求。

### 8.4 发布质量与安全建议

- 每个版本提供版本号、各平台产物和 SHA-256 校验值，说明如何通过可信渠道获取并校验；校验值的可信分发方式待设计。
- 每个正式支持的系统与架构都应有对应的构建及运行验证，至少覆盖版本查看、API、Git 集成和 MCP stdio 的基本流程；测试依赖的 Git 及 Gitea 环境需在验收方案中列明。
- 评估 macOS 代码签名与公证、Windows 代码签名及团队设备策略。签名和公证所需的账号、证书和成本需确认；Windows 签名本身也不保证消除所有 SmartScreen 提示。参考 [Apple 公证说明](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)和 [Microsoft 代码签名说明](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)。
- 首版采用系统 Git，安装说明须列出 Git 依赖及检查方式；最低版本和凭证管理器验证方案见 [platform-support.md](platform-support.md)，纯 API 不因未安装 Git 而不可用。Git 版本下限不代表旧补丁版本仍获安全维护。

### 8.5 待确认

- 团队实际使用的 macOS、Windows 版本和 CPU 架构，以及 Windows ARM 的验证条件。
- 是否有 Linux CI、容器或服务器使用需求。
- Gitea 发布页面是否作为唯一下载入口，是否需要包管理器或内网镜像。
- macOS 与 Windows 的签名证书、设备管理和发布权限条件。
- 是否需要自动更新；若需要，须另行确定触发、验证、回滚和离线行为。
