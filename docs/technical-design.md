## 1. 目标与设计边界

本设计描述面向自部署 Gitea 的 CLI、Git 集成、通用 API 和本地 MCP 服务。项目使用 Go 1.27.3 构建，交付 macOS 和 Windows 预编译程序；首版同时覆盖通用 API 调用及常用业务操作。首版业务命令为第 4 节全部已列命令，包含交互补全和无参数菜单；工具清单见 [MCP 设计](mcp-design.md)。

命令名为 sotea，首版运行、认证、多选和确认契约见 [cli-contract.md](cli-contract.md)。本文及该契约共同约束实施；依赖版本、真实平台支持与服务端行为仍需验证。版本兼容目标为 28.3.0、1.27.3、1.26.4、1.25.5、1.24.7、1.23.8 和 1.22.6；七版本产物已固定摘要并完成 P0 环境演练，P2 认证／仓库只读及 P3 Issue 通过；P4 PR／Release 结果另见阶段记录；完整 MCP 与平台验收仍待完成。具体证据见 [p0-readiness.md](p0-readiness.md)。

## 2. 总体架构

建议使用一个可执行程序，提供 CLI、无参数终端菜单和 stdio MCP 服务。各入口调用同一应用服务，统一处理仓库上下文、权限、API 版本差异和错误。MCP 直接调用应用服务，不通过运行 CLI 子进程并解析文本输出实现。不同运行入口分别启动进程，共用可执行文件和配置，并不意味着共享内存或运行中的服务进程。

~~~mermaid
flowchart LR
    CLI[CLI 命令] --> APP[应用服务]
    TUI[终端菜单] --> APP
    MCP[MCP stdio 服务] --> APP
    APP --> CTX[实例和仓库上下文]
    APP --> GIT[Git 适配器]
    APP --> API[Gitea API 客户端]
    APP --> AUTH[配置和凭证]
    API --> COMPAT[版本能力适配]
    GIT --> SYSTEMGIT[本机 Git]
    API --> SERVER[Gitea 实例]
~~~

| 组件 | 职责 |
| --- | --- |
| CLI 入口 | 参数解析、交互、输出格式与进程退出状态。 |
| 终端菜单 | 持续会话、仓库上下文展示和操作导航；调用应用服务。 |
| MCP 入口 | 协议生命周期、工具描述、输入校验及结构化结果。 |
| 应用服务 | 定义业务操作与共用流程，不依赖终端或 MCP 传输。 |
| 上下文 | 解析实例、账号、本地仓库和远程仓库，处理歧义。 |
| Git 适配器 | 调用系统 Git、读取仓库上下文、按需访问凭证辅助程序。 |
| API 客户端 | 认证、HTTP 请求、分页、上传下载、错误及取消。 |
| 兼容层 | 获取服务端版本，按操作适配已验证的差异。 |
| 配置与认证 | 管理多实例配置、凭证引用和安全存储。 |

## 3. 工程组织与依赖

程序生成的帮助、提示、确认、表头、菜单、错误、诊断与 MCP 用户可见摘要统一使用英文；远端用户内容及 Git／通用 API 原始流保留原文。开发文档和 GoDoc 继续使用中文。

开发、CI 和发布构建使用 Go 1.27.3；工具链升级应经过兼容性和测试评估。HTTP、进程管理及基础编码优先评估标准库。CLI 命令解析已引入 Cobra，P5 终端样式已采用 Lip Gloss v1.1.0，交互组件见第 4.8 节；Cobra 的锁定版本以 go.mod 为准，实际依赖与许可说明见各阶段交付记录。MCP SDK 已锁定官方 go-sdk v1.8.0，系统凭证库为 go-keyring v0.2.8，安全终端边界使用 x/term v0.47.0；许可证、实现边界及平台证据见 [P2 记录](p2-readonly.md)。

建议目录如下，名称和边界可随实现调整：

~~~text
cmd/sotea/           程序入口
internal/cli/        命令行适配
internal/tui/        持续菜单和交互选择
internal/mcp/        MCP 服务及工具
internal/app/        应用服务
internal/context/    实例与仓库上下文
internal/git/        Git 进程和仓库信息
internal/gitea/      HTTP API 客户端
internal/compat/     版本能力与适配
internal/config/     配置读写
internal/auth/       凭证来源及存储
internal/output/     输出和脱敏
testdata/            测试数据
tests/integration/   集成测试
docs/                设计与使用文档
~~~

依赖方向为入口层调用应用层，应用层通过明确接口调用基础设施；基础设施不依赖 CLI 或 MCP 的输出格式。接口以实际变化边界为依据，避免为每个函数抽象接口。

## 4. 命令与上下文

### 4.1 范围与设计约定

本节以 [Gitea 28.3.0 API 文档](https://docs.gitea.com/api/)和 [OpenAPI 定义](https://docs.gitea.com/openapi3-28.json)为例，优先设计 Issue、PR 和 Release 的常用命令，仓库、分支、标签及提交状态作为工作流支撑。下表全部命令和交互设计纳入首版；七版本必须通过对应功能验收，通用 API 继续访问实例实际支持的全部端点。API 映射以 28.3.0 举例，不等于其他版本也使用相同端点或字段。

下表路径均相对于实例的 API 根路径 /api/v1；R 表示 /repos/{owner}/{repo}，N 表示仓库内 Issue 或 PR 编号，ID 表示 Release ID。仓库、编号和标签应按路径段编码；Release 的标签名与 ID 不能混用。

各表的“交互式设计”为首版范围，Issue 和 PR 关闭／重开支持多资源目标；其余业务写操作单资源目标，多值字段可多选，详见 CLI 契约第 5 节。所有业务写入即使直接传编号也确认，非交互完整参数加 --yes。除用户主动进入交互外，仅在必需目标或参数缺失时考虑提示；已明确提供的参数不应被交互覆盖。表格中的单选、多选分别指选择目标的方式，不代表相应接口支持批量写入。交互条件、取消和非终端行为统一遵循第 4.8 节。

### 4.2 Issue

| 首版命令 | 操作 | 28.3.0 API | 交互式设计 |
| --- | --- | --- | --- |
| issue list | 列表、状态及标签等筛选 | GET R/issues | 子命令默认直接分页列出；持续菜单支持搜索和分页浏览。 |
| issue view N | 查看详情 | GET R/issues/{index} | 缺少编号时搜索 Issue 并单选。 |
| issue create | 创建 Issue | POST R/issues | 缺少标题等必需输入时提示填写；正文、标签和负责人等可选项按用户选择补充。 |
| issue edit N | 编辑标题、正文及里程碑等 | PATCH R/issues/{index} | 缺少编号时单选；未指定修改内容时选择要修改的字段并输入新值。 |
| issue close N | 关闭 Issue | PATCH R/issues/{index}，设置关闭状态 | 缺少编号时从未关闭 Issue 中搜索并勾选一个或多个；确认与批量结果见第 4.8 节。 |
| issue reopen N | 重新打开 Issue | PATCH R/issues/{index}，设置打开状态 | 缺少编号时从已关闭 Issue 中多选，最多 100 个；直接传编号也确认。 |
| issue comment list N | 查看普通评论 | GET R/issues/{index}/comments | 缺少编号时单选 Issue，然后列出评论。 |
| issue comment add N | 添加普通评论 | POST R/issues/{index}/comments | 缺少编号时单选 Issue；缺少评论内容时提示输入。 |
| issue assignee add N / remove N | 添加或移除负责人 | 1.27.3、28.3.0 定义中有 POST / DELETE R/issues/{index}/assignees；旧样本需评估整体替换的并发风险，见多版本调研。 | 缺少编号时单选 Issue；添加时选择或输入负责人，移除时从当前负责人中勾选。 |
| issue label list N | 查看 Issue 标签 | GET R/issues/{index}/labels | 缺少编号时单选 Issue，然后列出标签。 |
| issue label add N / remove N | 添加或移除标签 | POST R/issues/{index}/labels；DELETE R/issues/{index}/labels/{id} | 缺少编号时单选 Issue；添加时从可用标签中勾选，移除时从当前标签中勾选。 |

Issue 列表应显式区分 Issue 和 PR：28.3.0 的列表接口提供 type 参数，Issue 命令应请求 issues 类型；其他版本的实现及回退需验证。标签操作区分增量添加、移除和整体替换，不能把添加实现为覆盖现有标签。里程碑使用编辑接口设置，清空语义及各版本字段支持需验证。

### 4.3 Pull Request

| 首版命令 | 操作 | 28.3.0 API | 交互式设计 |
| --- | --- | --- | --- |
| pr list | 列出 PR | GET R/pulls | 子命令默认直接分页列出；持续菜单支持搜索和分页浏览。 |
| pr view N | 查看 PR | GET R/pulls/{index} | 缺少编号时搜索 PR 并单选。 |
| pr create | 创建 PR | POST R/pulls | 缺少时逐项补齐：当前分支作 head 候选、仓库默认分支作 base 候选；跨仓库 head 显式输入，不自动 push。 |
| pr edit N | 编辑 PR | PATCH R/pulls/{index} | 缺少编号时单选；未指定修改内容时选择字段并输入新值。 |
| pr close N / reopen N | 关闭或重新打开 PR | PATCH R/pulls/{index} | 缺少编号时多选相应状态的未合并 PR，最多 100 个；直接传编号也确认。 |
| pr files N / commits N | 查看变更文件或提交 | GET R/pulls/{index}/files；GET R/pulls/{index}/commits | 缺少编号时单选 PR，然后直接显示对应结果。 |
| pr comment list N | 查看普通讨论评论 | GET R/issues/{index}/comments | 缺少编号时单选 PR，然后列出普通评论。 |
| pr comment add N | 添加普通讨论评论 | POST R/issues/{index}/comments | 缺少编号时单选 PR；缺少评论内容时提示输入。 |
| pr review list N | 查看审查记录 | GET R/pulls/{index}/reviews | 缺少编号时单选 PR，然后列出审查。 |
| pr review create N | 提交审查意见 | POST R/pulls/{index}/reviews；已有审查提交使用 POST R/pulls/{index}/reviews/{id} | 缺少编号时单选 PR；按审查类型和内容要求提示输入，并明确最终提交的审查结果。 |
| pr reviewer add N | 请求审查 | POST R/pulls/{index}/requested_reviewers | 缺少编号时单选 PR；输入明确审查者账号，或通过参数提供组织团队；不枚举全站账号，服务端权限及读回共同核验。 |
| pr merge N | 合并 PR | POST R/pulls/{index}/merge | 缺少编号时从待合并 PR 中单选；展示目标、合并方式并按已确认策略提示，具体可选方式以实例及仓库规则为准。 |

PR 普通评论使用 Issue 评论接口；审查记录、审查评论和代码行评论使用 PR 审查相关接口，不能视为同一种评论。代码行评论专用命令不在首版，普通评论和 PR 级审查均纳入。创建 PR 需要明确源分支与目标分支，跨仓库参数依服务端能力验证；合并方式、是否删除源分支及交互确认应由用户显式选择或按已确认默认值执行，权限、冲突和仓库保护规则由服务端判定，失败不能当作成功。

### 4.4 Release

| 首版命令 | 操作 | 28.3.0 API | 交互式设计 |
| --- | --- | --- | --- |
| release list | 列出版本 | GET R/releases | 子命令默认直接分页列出；持续菜单支持搜索和分页浏览。 |
| release view TAG | 按标签查看 | GET R/releases/tags/{tag} | 缺少标签时从已有 Release 中单选。 |
| release create TAG | 创建 Release，可指定草稿、预发布及说明 | POST R/releases | 缺少标签时选择已有标签或明确输入新标签；名称、说明、草稿和预发布选项可按用户选择填写。新标签行为需服务端验证。 |
| release edit TAG | 修改名称、说明、草稿或预发布状态 | GET R/releases/tags/{tag} 获取 ID，再 PATCH R/releases/{id} | 缺少标签时单选已有 Release；未指定修改内容时选择字段并输入新值。 |
| release asset list TAG | 查看附件 | 按标签查询 ID，再 GET R/releases/{id}/assets | 缺少标签时单选已有 Release，然后列出附件。 |
| release asset upload TAG FILE | 上传附件 | 按标签查询 ID，再 POST R/releases/{id}/assets | 缺少标签时单选已有 Release；缺少文件路径时提示输入，首版一次上传一个文件，不提供额外原生文件选择器。 |

Release 与 Git 标签是不同资源。创建 Release 对不存在标签的处理、标签指向、草稿发布规则和重复附件处理，需要结合服务器版本、权限及团队约定验证；失败时明确报告实际已完成的步骤。上传采用接口要求的文件表单，流式处理文件，报告文件过大、无权限或网络中断；写入结果未知时先查询服务器再决定是否重试。Release 或附件删除和附件下载不提供首版专用命令，可使用通用 API；草稿创建、发布和同名冲突规则见 CLI 契约第 7 节。

### 4.6 使用示例和输出

以下展示首版入口，完整行为和默认值以 CLI 契约为准，示例不代表已实现：

~~~sh
sotea issue list --repo acme/demo --state open
sotea issue create --repo acme/demo --title "修复登录问题" --body "问题描述"
sotea pr create --repo acme/demo --base main --head feature/login --title "修复登录"
sotea pr review list 42 --repo acme/demo
sotea pr merge 42 --repo acme/demo
sotea release create v1.0.0 --repo acme/demo --draft --notes-file notes.md
sotea release asset upload v1.0.0 ./build/app.zip --repo acme/demo
sotea api --instance team --method GET /repos/acme/demo
~~~

列表建议默认一页，支持显式分页与全部页获取；字段、筛选和默认排序按各端点能力确定。普通命令建议提供人类可读和 JSON 输出，正常结果写 stdout，诊断信息写 stderr。非交互式写入必须提供必要输入，禁止意外进入交互；通用 API 保留原始响应和文件流能力。

### 4.7 终端兼容与输出样式

#### 支持目标与库选择

CLI 以 macOS Terminal、iTerm2 和 Windows PowerShell 为终端使用目标。PowerShell 是 shell，实际样式还取决于其所在终端宿主；Windows 验证至少覆盖 Windows Terminal。具体系统、PowerShell 5.1／7.6 LTS、传统控制台的提案及验收矩阵见 [platform-support.md](platform-support.md)，目前没有实测兼容结论。

| 组件 | 选择 | 职责 |
| --- | --- | --- |
| 命令与参数 | [Cobra](https://github.com/spf13/cobra) | 命令层级、参数、帮助及 shell 补全。 |
| 输出与布局 | [Lip Gloss](https://github.com/charmbracelet/lipgloss) | 彩色、加粗、对齐、边框与表格布局。 |

Cobra 的版本已在 go.mod 中锁定；P5 已直接使用 Lip Gloss v1.1.0、termenv v0.16.0 和 uniseg v0.4.7，沿用已有版本，许可与平台证据见 P5 记录。键盘选择组件及是否需要持续会话界面见第 4.8 节。业务数据和应用服务不依赖终端样式库，文本渲染集中在输出层。

#### 输出契约

- 交互式终端默认输出可读文本：Issue、PR 和 Release 列表可使用带表头的表格，状态和重点信息可用颜色或加粗辅助区分；信息不能只依靠颜色表达。详情及错误按内容选择合适布局。
- 建议提供 `--color=auto|always|never`：默认 `auto`，按对应输出流是否连接终端及终端能力判断；`always` 显式启用颜色，`never` 显式关闭。未显式设置颜色选项时尊重非空的 `NO_COLOR`；显式选项优先。stdout 与 stderr 分别判断，不因其中一个连接终端就假定另一个也连接。
- 管道和文件重定向在默认 `auto` 模式下不输出 ANSI 颜色，也不输出动画或动态进度；`--color=always` 允许用户有意输出颜色。检测不到终端能力时使用可读的无样式文本。
- JSON 输出保持可机器解析：stdout 仅含 JSON，不混入颜色、表格、进度或提示。通用 API 的原始响应及下载内容不做样式包装或修改；错误与诊断写入 stderr。
- MCP stdio 的 stdout 仅承载协议消息，不经过终端渲染；诊断写入 stderr，不向协议流输出进度、交互提示或 ANSI 样式。
- Git 透传入口继承 Git 的终端输入输出和颜色配置，不对 Git 输出二次着色或排版。
- 持续界面用固定语义角色区分层级：主要操作蓝色加粗、辅助说明灰色弱化、返回操作橙色加粗，Run with options · filters and advanced fields 紫色加粗，分组章节使用统一青绿色加粗。具体 ANSI 色号集中在输出组件。关闭颜色、NO_COLOR 生效或终端不支持样式时保留文字、顺序和操作含义。
- 详情中的顶层章节以可复用的章节组件着色并分页。视口足以容纳当前组时完整显示该组；单组超过视口才允许组内滚动。PageUp／PageDown 切换顶层组，Tab／Shift+Tab 是替代按键；↑／↓、Home／End 滚动当前长组。嵌套章节留在父组中。章节元数据与正文一起传递，显示缓冲被截断时不得进入可接受的确认输入。左右键和 h／l 不用于切组，供当前选择项的备选值交互使用。
- 表格根据可用宽度布局，对中文、Emoji、长标题、空值及窄终端进行显示宽度处理；需要截断时给出可识别标记，并保留通过详情或 JSON 获取完整数据的方式。纯文本默认值和具体列集合待命令契约确定。
- 渲染服务端返回的标题和正文时，避免把其中的终端控制字符当作控制序列执行；JSON 与通用 API 原始输出保持其各自的原始语义。

示意如下，颜色和加粗在此纯文本示例中不展示：

~~~text
#    STATE   TITLE             ASSIGNEE   LABELS
42   OPEN    修复登录问题      chiyoshi   bug
38   OPEN    增加发布流程      alice      enhancement
~~~

### 4.8 交互式命令与目标选择

#### 4.8.1 目标与范围

首个场景是用户执行 `sotea issue close` 时没有指定 Issue 编号，CLI 自动查询当前目标仓库的未关闭 Issue，展示可搜索、可勾选的列表，让用户选择一个或多个目标并执行关闭。参数齐全时保留直接指定目标的方式，写入仍须确认或显式 --yes。

本节的命令参数选择器适用于单条命令执行期间；持续菜单界面是第 4.8.6 节的补充方案。不假设用户必须使用自然语言、AI 服务或额外 API 密钥。Issue 选择器的输入、分页、展示和取消机制用于当前表中所有交互命令，多选范围按 CLI 契约。

#### 4.8.2 Issue 关闭流程

1. 解析显式实例与仓库，或按第 4.5 节解析本地上下文；无法唯一确定时先解决歧义，再展示候选 Issue。最终目标实例和仓库须始终可见。
2. 未提供编号且满足交互条件时，通过共享应用服务查询 Issue：请求 `GET R/issues`，显式使用 `state=open` 和 `type=issues`，分页加载。按第 7 节处理各版本能力和鉴权，不将 PR 混入 Issue 列表。
3. 列表至少展示编号、标题和状态，可视空间允许时展示负责人和标签；以编号作为选择值，而非标题或列表位置。支持键盘移动、勾选／取消、搜索、加载后续页和取消退出；禁止默认选中第一项。标题中的控制字符不能作为终端控制序列执行。
4. 选择或直接传入编号后展示目标仓库及完整已选编号，再由用户确认关闭；默认不确认，--yes 可显式跳过。未选择目标或在提交前取消时不发起关闭请求。实际按键与确认文案在终端验收时确定。
5. 按用户选择向服务端发送关闭操作：对每个编号执行 `PATCH R/issues/{index}` 并设置关闭状态；遵守版本兼容、权限和超时策略。批量操作不是事务，逐项记录成功、跳过、失败、结果未知及未执行的编号，汇总给用户；若存在失败或结果未知，返回非零退出状态。已达目标状态报告 skipped，退出码及逐项结果按 CLI 契约第 6 节。
6. 某项请求超时或断线时标记结果未知，不自动重试；用户取消发生在提交过程中时停止尚未开始的请求，已完成的不回滚，进行中的请求按实际结果或未知状态报告。

交互示意（P3 已实现基础选择与确认，完整样式按 P5 实施）：

~~~text
$ sotea issue close --repo acme/demo
Select issues to close (repository: acme/demo)
Search: login

  [x] #42  OPEN  修复登录问题          chiyoshi
  [ ] #38  OPEN  更新登录文档          alice
  [x] #35  OPEN  清理登录过期提示      bob

↑↓ Move  Space Select  / Search  Enter Continue  Esc Cancel
Close #42, #35 in acme/demo? [y/N]

Closed #42
Closed #35
~~~

支持 issue close 42 和 issue close 42 35，PR 关闭／重开及 Issue 重开使用相同多目标语法，最多 100 个目标。直接传编号也确认；--yes 只跳过确认，不能在缺少目标时自动勾选。脚本需完整参数加 --yes。

#### 4.8.3 候选列表、搜索与并发

- 默认先获取一页并按需加载后续页面，不将当前页标为全部结果；展示加载状态、当前筛选条件及已选择数量。按实例配置、服务器分页上限和资源限制控制请求量，不在后台无限拉取所有 Issue。
- 支持跨已加载页面保留勾选，并按实例、仓库和 Issue 编号去重。P3 Issue 搜索在完整有界查询集上计算标题／正文子串匹配，不依赖异步索引；多标签按任一匹配后分页，超过 10000 项明确报错。其他资源优先采用已验证的服务端搜索；如仅筛已加载数据，必须标注范围。
- 搜索条件变化或翻页后，已选项目保持可检查、可取消；确认前列出全部已选编号，不能只展示当前页。默认没有全选或批量修改隐藏结果的行为。
- 分页期间服务端数据可能变化，不能假设列表是原子快照。提交时按所选编号逐项调用服务器；目标已关闭、被删除或权限发生变化时，按实际响应报告，不能把未执行或失败项当成成功。预先重新读取也不能消除读取到写入之间的竞争。

#### 4.8.4 交互判定与输出

默认仅当 stdin、stdout 和 stderr 均为可交互终端，且没有明确选择非交互或机器输出模式时启动选择器。CI、管道、重定向、缺少终端或用户显式要求非交互时，缺少编号应立即报错并提示如何传入编号，不等待输入、不自动选择。首版提供 --no-interactive 禁止提示，不提供绕过终端检测的强制交互选项；--yes 不改变终端判定。

交互界面写入终端诊断流，最终操作结果写 stdout，错误写 stderr；JSON 模式的 stdout 只包含结构化结果。MCP 使用协议参数显式传递 Issue 编号或编号列表，不启动 CLI 选择器或读取 MCP 的 stdin；CLI 与 MCP 复用相同的查询和关闭应用服务。两者的确认机制分别设计，不能把客户端展示当成服务端权限控制。

#### 4.8.5 组件与验证

P3 动态选择器已采用 Bubble Tea v1.3.10 和 go-runewidth v0.0.16，支持分页、搜索、稳定 ID 跨页保留及已选回查。标准输出保留最终结果，界面使用 stderr；异步请求用取消和轮次 ID 排除过期响应。POSIX PTY 成功／取消场景已验证；Terminal、iTerm2 和 Windows 宿主实测仍单独记录。Huh 未引入；P5 已接通共享字段表单、持续菜单、静态降级和样式，详见 [P5 记录](p5-terminal-experience.md)。

测试应覆盖单选、多选、搜索、跨页保留选择、重名标题、编号去重、空列表、获取失败、过期状态、权限错误、部分成功、结果未知、提交前后取消、非终端、JSON / CI 模式，以及 macOS Terminal、iTerm2、Windows Terminal 中的 PowerShell。使用可控服务与终端模拟进行自动化验证，再在目标终端和隔离 Gitea 实例验证完整流程。

#### 4.8.6 持续菜单界面（首版纳入）

P5 根据 iTerm2 实机反馈修订为单一 Bubble Tea 程序：菜单导航与单选 Enter 接受，批量资源才用 Space；Esc 返回直接上级并保留焦点。输入、隐藏 token、完整预览、可取消加载和可滚动结果共用屏幕，结果不退屏写入 shell。Run with options 提供可选筛选，默认只读直接执行。子选择器异步消息同时检查页面代数和请求编号，离开页面取消并等待 provider；Git／原始 API 使用 tea.Exec 暂停与恢复真实终端。启动先匿名验证版本，已登记来源才核对身份和仓库；不可用时关闭业务菜单，保留修复入口，检测失败不等同非 Gitea。修订证据与旧产物分开，见 P5 记录第 7 节。

详情／JSON 章节分页与持续选择器采用不同页面语义：菜单和候选仍以 ↑／↓ 移动选项；结果详情按完整顶层组浏览，PageUp／PageDown 与 Tab／Shift+Tab 切组，长组内部可滚动。标题角色元数据由本地渲染器产生，远端字段只作为普通文本，不能声明章节或颜色角色。Run with options 由稳定菜单项角色标记，不依据可变标题内容猜样式。

### 4.8.7 账户仓库目录

Home 的 Browse account 使用应用目录服务，不遍历实例仓库，也不从当前 Git worktree 推断账户范围。调用 GET /user/repos 展示 API 对已验证账号返回的仓库，GET /user/orgs 展示其组织成员关系；组织仓库使用 GET /orgs/{org}/repos。界面使用 Account repositories 这一中性名称，避免暗示具有实例级全量权限。

目录服务分页上限为每页 30 项，筛选仅作用于当前响应页。组织列表项以稳定组织 ID 作选择键，进入组织仓库前重新读取 /orgs/{org} 并核对 ID；仓库列表项以稳定仓库 ID 作选择键，进入工作台前重新读取 /repos/{owner}/{repo} 并同时核对 ID 与 full_name。账号身份需与验证响应一致，返回上层保留原页、筛选和焦点。

仓库工作台把实例、已验证账号和远端仓库固定为一次浏览作用域，使用现有仓库应用服务。该工作台不将启动目录中的本地 Git 上下文带入，不显示本地 Git 操作，不克隆、不改写 remote 或保存默认配置。每次网络动作重新解析配置；实例、账号或配置修订不再匹配初始作用域时，在发送凭证前停止，并要求从 Home 重新打开浏览。浏览器加载使用可取消的短生命周期 context；本地目录服务验证身份、稳定 ID、分页边界与取消，真实七版本／终端验收状态以开发计划为准。

## 5. Git 集成

### 5.1 执行与仓库发现

首版调用系统 Git，以复用用户已有配置、凭证辅助程序和 SSH 环境；需要 Git 的操作应报告缺失的 Git，并允许后续评估配置可执行文件路径。仅调用 Gitea API 的场景不依赖安装 Git。Git 最低支持版本尚待实测确定。

通过参数数组启动进程，不将用户参数拼接为 shell 命令。CLI 透传入口继承终端输入输出，保留 Git 的正常退出码和交互；启动失败、收到信号或被取消时单独报告。覆盖 Windows 路径、参数引用和子进程清理。

通过 Git 自身查询仓库根目录、当前分支和 remote，支持子目录、worktree 和 .git 为文件等情况。解析 HTTPS、SSH 和常见 SCP 风格 remote，并考虑端口、服务子路径、SSH 主机别名、fork 和多个 remote。SSH 地址无法确定 HTTP 实例时使用配置映射或要求显式指定，不能仅凭相似主机名猜测。

### 5.2 凭证与非交互执行

Git 远程操作继续使用 Git 配置的凭证辅助程序或 SSH 机制。API 认证与 Git 认证分开管理；首次登录优先复用经验证的 Git HTTPS 凭证来源，在目标仓库的 Git 配置上下文中调用 git credential fill。匹配包括协议、主机及显式端口、已知用户名和由 credential.useHttpPath 控制的仓库路径；HTTP(S) 默认不按仓库路径区分外部 helper 中的凭证，不是仅按域名匹配，也不默认每仓库独立登录。完整规则、来源映射和验收见 [CLI 契约第 4.3 节](cli-contract.md#43-git-凭证匹配与复用范围)。获取到的密钥仅在所需期间保存在内存，不读取 SSH 私钥内容，不写入日志。

MCP 的 stdin 和 stdout 属于协议连接，不可交给 Git 进程。MCP 中的 Git 调用须捕获输出、禁止交互、设置超时，响应取消并清理子进程；还需处理辅助程序或 SSH 仍可能阻塞的情况。MCP 首版仅提供固定的 Git 上下文读取，不暴露任意 Git 子命令或 Git 写操作。

## 6. Gitea API 客户端

### 6.1 通用调用

通用入口允许选择实例、HTTP 方法、API 路径、重复查询参数、请求头及请求体，并支持 JSON、原始内容、文件上传及流式下载。保留状态码、必要响应头和原始响应体供脚本或调用者处理；不得依赖已登记的业务端点白名单。用户可访问的具体 API 仍受实例支持范围、服务器配置及账号权限约束。

实例地址可能包含反向代理子路径；URL 构造需正确编码路径段与查询参数，防止路径穿越以及将凭证发送到其他来源。重定向跨来源时不自动转发认证信息。默认校验 TLS，支持显式配置私有 CA；证书策略和代理行为需有文档。

建议默认只请求一页；自动获取全部页面须显式启用，并设置页数或数量上限及重复页检测。请求支持超时和取消；只对适合重试的读取请求执行有界重试，写请求默认不自动重试。写入后连接中断时报告结果未知，提示用户查询服务器状态，避免误报失败后重复创建。大文件流式处理；下载文件使用临时文件并在成功后替换目标的具体规则待确认。

### 6.2 业务操作

应用服务提供 Issue、Pull Request、Release 及开发上下文等常用操作，首版命令与 28.3.0 接口映射见第 4 节，参数经验证后交给 API 客户端。各命令按本节及 CLI 契约实施，不再以候选清单处理；JSON 输出使用第 10 节链接的共同契约。通用 API 覆盖入口与业务命令并行：能构造服务器支持的请求并不意味着每个端点都有专用命令，或全部端点均经过逐版本测试。

## 7. Gitea 多版本兼容

### 7.1 检测与适配

七个目标版本的官方 API 定义均包含 `GET /api/v1/version`，成功响应的 ServerVersion 模型包含字符串字段 `version`。客户端先获取实例声明的版本，再结合具体操作的能力矩阵选择请求形式；版本声明本身不能证明端点存在、账号有权限或自定义构建行为与官方版本一致。各版本的定义依据和差异见[多版本调研](gitea-api-compatibility.md)。

兼容层按具体操作维护能力与已验证的请求、响应差异，避免每个版本复制一套完整客户端。版本判断、字段适配与响应解析集中测试。可选字段必须区分未提供、零值和清空；服务器不支持用户指定的字段或语义时应报错，不静默丢弃字段或改变写入含义。真实差异以各版本 API 定义及实际测试为依据，不预先假定。

七个目标版本的官方 API 定义对比及 CLI 适配建议见 [Gitea API 多版本差异调研](gitea-api-compatibility.md)，逐项机器生成结果见[差异明细](gitea-api-differences.md)。兼容策略结合静态定义、源码核对与 P2 七版只读实测；P3 七版本 Issue 与通用 API 结果见 [P3 记录](p3-issue.md)；PR／Release 和完整 MCP 仍待验收。

#### 7.1.1 获取远端版本

实例配置保存 Gitea 的完整根地址；在此基础上追加 `/api/v1/version`，而不是从 Git remote 的路径或域名猜测版本。例如：

| 实例根地址 | 版本请求地址 |
| --- | --- |
| `https://git.example.com` | `https://git.example.com/api/v1/version` |
| `https://git.example.com/gitea` | `https://git.example.com/gitea/api/v1/version` |

请求示例（响应仅为格式示意）：

~~~sh
curl --fail https://git.example.com/api/v1/version
# {"version":"1.27.3"}
~~~

流程如下：

1. 使用与业务 API 相同的实例配置、TLS / 私有 CA、代理与所选账号认证；不能自动枚举或尝试其他实例和账号的凭证。无需账号的实例可在无凭证时请求，权限限制以服务端响应为准。
2. 发送可取消的 GET 请求；建议默认超时 5 秒，具体值可配置，使用有界响应大小。遵守已有的同源认证与重定向规则，跨来源不得自动转发凭证。
3. 在成功响应中解析 JSON 对象的非空字符串 `version`；空字段、非 JSON 内容或异常格式均视为未知，不能把代理返回的 HTML 错误页当成成功识别。
4. 同时保存原始版本、解析结果、实例根地址、获取时间及来源；实际可获得的实例标识和构建信息不能仅凭版本字符串推断。该流程不假设请求一定匿名可用，也不假定 Swagger 文档必然开放。

#### 7.1.2 版本解析与证据

版本解析器应同时接受本次目标中的 `1.27.3` 与 `28.3.0` 等版本，不把主版本固定为 1。保留原文；只在解析规则明确时提取版本组成，开发版、预发布、构建元数据、自定义后缀及不可解析版本不能被截断后冒充已测试的正式版本。

能力判断分别保存：**检测状态**（已识别 / 未知）、**API 定义证据**（已列出 / 未列出 / 未调研）、**实例测试证据**（已通过 / 未测试 / 已失败），以及运行时实际返回结果。官方精确版本号与静态定义匹配，只表示可以选取相应的候选适配规则，不代表目标实例已通过测试；版本号也不能证明它不是定制构建或其他兼容实现。

适配表以操作、必要字段和筛选参数为粒度，精确记录证据和请求模型，例如：

| 例子 | 定义对比结果 | 客户端处理 |
| --- | --- | --- |
| Issue 负责人新增 | 1.27.3、28.3.0 的定义列出独立 POST；五个较早样本未列出 | 精确匹配时选择相应候选策略；旧版整体替换有并发覆盖风险，不能静默视作等价操作。 |
| PR 合并字段 | 1.25.5 与 1.26.4 的定义字段命名不同；新版源码包含旧名称兼容 | 根据已验证的规则选择序列化方式；合并失败或超时不得自动更换字段并重复写入。 |
| Release 标签筛选 | 28.3.0 的定义列出 `tag_filter`；1.27.3 等其余样本未列出 | 无已验证等价策略时返回明确的筛选不支持或待确认，不能忽略该条件。 |

这些例子都只是静态定义和源码证据，真实实例回归仍待执行。规则覆盖范围仅限列出的精确版本；其他补丁版本、分支及自定义构建不得自动套用“已验证”标签。未来扩大支持范围时，必须先补充证据并更新矩阵。

#### 7.1.3 失败、权限与未知版本

| 情况 | 判断与行为 |
| --- | --- |
| 超时、DNS、TLS 或网络错误 | 记录版本检测失败的具体类别，提供排查信息；不能当作不兼容。 |
| 401 / 403 | 标记认证或权限失败，不断言 API 或版本不支持。 |
| 404 | 标记版本入口不可用或地址待检查；可能与子路径、代理、权限或接口有关，不能单独断言不支持。 |
| 200 但 JSON 无效、缺少版本或版本无法解析 | 版本未知，保留适合诊断的状态；不猜测兼容版本。 |
| 已识别但未纳入目标矩阵 | 返回未验证状态，不把它判为不兼容，也不宣称已支持。 |
| 通用 API 请求 | 不以前置版本检测作为请求门槛；按用户明确指定的请求调用，并保留服务端状态和响应。 |
| 专用业务命令 | 只选择有证据的请求策略；未能确定写入语义时返回可识别错误和可操作提示，不执行有副作用的猜测或自动回退。只读命令可提供明确的尝试路径，但不能把尝试成功扩大为其他 API 均兼容的结论。 |

同一个已知版本的业务请求仍可能因 token scope、账号权限、仓库不存在、禁用功能、代理或服务器配置失败；兼容矩阵不替代服务端权限检查。不要通过创建 Issue、合并 PR 等有副作用的请求来探测能力，也不要把一次业务请求的 403 / 404 永久缓存成该版本不支持。

#### 7.1.4 缓存和实例变更

建议仅在进程内缓存检测结果：普通 CLI 进程结束后自然失效；长驻 MCP 进程建议成功结果缓存 5 分钟、失败结果最多缓存 30 秒，数值可配置且应受验证。缓存按规范化后的完整实例根地址（含 scheme、主机、端口、子路径）与所选账号上下文隔离，不存储 token、原始响应敏感内容或仓库权限判断。

实例地址、账号、凭证引用、TLS / CA 或代理配置变更时使相关缓存失效；凭证轮换等可能不改变引用的场景需提供显式刷新。超过有效期重新检测，合并并发的同一实例检测请求；检测支持超时和取消。TTL 只能减少过期窗口，不能保证版本立即变化时的实时一致性。重大写操作需要在缓存仍有效的前提下使用已知策略；失效或状态未知时先刷新并按上述失败规则处理。缓存不持久化，以免下次运行误用旧版本。

#### 7.1.5 用户可见诊断

首版提供实例诊断入口，输出沿用 CLI 契约的结构化结果：

~~~sh
sotea instance info --instance team --refresh
sotea instance info --instance team --refresh --json
~~~

展示实例根地址、服务端原始版本、检测状态、检测时间、是否来自缓存、匹配的精确版本以及“定义已分析 / 实例测试状态”；不把其中任何一项笼统显示成“全部 API 兼容”。客户端自身的 `sotea version` 保留为显示 CLI 版本，两者含义不同。MCP 复用同一版本检测服务，并以结构化方式返回相同诊断；stdout 仍只承载 MCP 协议。

#### 7.1.6 验证

单元及 HTTP 契约测试覆盖七个精确版本、带子路径的实例、合法与异常 JSON、带后缀和未知版本、超时、取消、TLS 失败、401 / 403 / 404、跨来源重定向、缓存隔离／过期／刷新，以及检测失败时通用 API 仍可直接执行。分别验证 CLI 与 MCP 选择同一能力规则，写入检测不会产生额外副作用。随后在七个隔离 Gitea 实例验证版本响应、权限和重点操作；不能用模拟服务代替实例测试。

### 7.3 七版本必需支持的实施规则

七个精确版本必须支持第 4 节的全部首版共同功能，以及认证、菜单、批量和 MCP 对同一业务的调用。原生端点缺失须完成适配后才能满足发布门槛；任何必需功能未验证、只返回不支持或没有可行适配时，正式发布阻断并记录实际问题，不能自行删掉目标版本。

共同功能的参数基线为：Issue 状态、关键词、标签、负责人及里程碑相关操作；PR 状态、源／目标分支、标题正文、负责人标签里程碑、普通评论、PR 级审查及审查请求、合并选项；Release 标签、目标提交、名称正文、草稿／发布、预发布和单文件附件。较新版本的 projects、tag_message、tag_filter、代码行回复／解决等仅是差异调研中的扩展，首版专用命令不增加这些专有字段；通用 API 仍可显式调用。

| 差异 | 首版适配和验收 |
| --- | --- |
| 较早样本没有独立负责人增删端点 | 新样本用原生端点；旧样本读取当前负责人集合，只计算用户要求的增删，再 PATCH 完整集合。写前重读、同进程串行、写后核对；发现变化或结果不符时报冲突／未知，不自动覆盖重试。预览必须说明旧版不是原子增删，--yes 表示接受该已说明操作语义；其他进程的并发更新仍可能覆盖，不能宣称全局无丢失。正常非并发增删及已知并发错误处理都须测试。 |
| PR 创建字段在旧版不足 | 以基础 PR 创建加已有的审查请求或编辑接口完成相同意图；先明确预览全部步骤。后续步骤失败时返回已创建 PR 和未完成步骤，不能重新创建 PR 或假装事务回滚。 |
| PR 合并字段改名 | 分版本构造各自文档对应字段，验证旧字段兼容而不依赖猜测；绑定 head SHA，失败不换一种字段自动重试合并。 |
| 筛选字段在旧样本不足 | 共同基线优先使用所有版本已具备参数；确需本地筛选时完整遍历目标查询集再筛选及分页，不先截一页造成漏项。默认最多扫描 10000 项，超限返回 FILTER_LIMIT 并要求缩小条件，不返回看似完整的部分结果。 |
| 可选响应字段或清空语义不同 | 业务模型区分缺失、零值和明确清空，忽略未知响应字段；清空里程碑、空负责人等必须按各版测试。能力探测不能用写请求。 |

旧版并发能力的限制是服务端边界，不因本地加锁而消失；若团队最终要求并发更新也必须原子无丢失，则需服务端支持或额外协作机制，当前版本矩阵不能通过客户端单独承诺。此处不减少首版操作范围，正常用户权限、受保护分支和真实冲突仍按业务错误处理。

七版本通过要求为需求 REQ-03、REQ-05 至 REQ-08，以及相同操作的 MCP 代表性回归，记录精确构建、账号权限、请求和实际结果。未知／未列版本单独按第 7.1 节处理，不能影响上述七版本的验收承诺。

## 8. 配置、认证与安全

首次启动默认从当前目录发现仓库、验证 Gitea 平台与身份，再继续业务命令或进入菜单。完整优先级、命令及生命周期见 [CLI 契约第 2–4 节](cli-contract.md)。

HTTPS Git 凭证通过 credential fill 查询并经 GET /api/v1/user 验证；无可复用凭证时配置独立 API token。SSH 登录不自动等于 API 登录，Git 的作者配置不等于远端账号。切换 sotea 账号不自动切换 Git SSH key；退出删除自有认证记录并按完整实例根地址及账号保存退出抑制标记，禁止下次经 helper 隐式重登或自动切换其他账号，保留仓库到实例的非敏感映射。清理共享 Git 凭证须单独选择并确认。

显式要求的 API 账号与 GET /user 身份不一致时返回 AUTH_IDENTITY_MISMATCH，禁止继续业务请求；只有交互式登录明确同意后才以实际账号建立绑定，--yes 和 MCP 不自动替换。比较 API 身份时不把 helper 占位用户名视作账号。环境 token 由 shell／客户端管理，退出须说明本地清理和环境来源仍存在，指导移除变量及重启继承旧环境的 MCP 进程，不宣称已删除或撤销该 token。退出、账号或凭证变化使长驻进程相关缓存与未提交计划失效；细则及验收见 CLI 契约第 4 节。

Git helper 查询使用所选 remote 的原始凭证上下文，并遵守 Git 的 useHttpPath 和配置匹配规则；sotea 自有 API 凭证引用绑定完整实例根地址和已验证账号。两类绑定不混用：同一实例多个仓库可复用同一引用，但同主机不同代理子路径的实例不能自动共用 API token。取得 Git 凭证后仍验证 API 身份与权限，approve / reject 必须说明实际影响范围。

非敏感配置采用 JSON，默认 os.UserConfigDir()/sotea/config.json；--config 或 SOTEA_CONFIG 可覆盖。密钥存于系统安全存储，CI 可运行时注入；保持原子写、并发更新检查、版本迁移和脱敏。401 与 403 分别处理，无明文静默回退。系统适配器及依赖版本已在 macOS 验证，Windows 运行仍待实机。

## 9. MCP 服务

Home 的 MCP integrations 负责四客户端的配置管理，不承载长驻协议服务。internal/mcpintegration 隔离客户端格式、条目托管、并发快照／备份／原子替换和临时 stdio 检查；internal/cli/mcp_integrations.go 只负责逐步输入和明确确认。配置修改不调用远端 API，不保存 token 或改写客户端批准策略；JSON／JSONC 精确编辑成员，Codex 通过独立 TOML 块管理，完整语法验证新增锁定 github.com/pelletier/go-toml/v2 v2.2.4，现有依赖和 Go 1.27.3 不升级。操作、所有权及恢复边界见 [接入说明](mcp-client-setup.md)。

首版工具及严格输入、输出方案见 [mcp-design.md](mcp-design.md)。同一程序以 sotea mcp serve 提供本地 stdio，客户端启动子进程，stdout 仅承载协议，EOF 清理退出；不依赖菜单进程，也不开放 HTTP 守护服务。

默认只读，--allow-write 显式提供 prepare / commit / status 工具；--allow-raw-api 单独开放通用 API，写请求仍需要写权限开关。写入先准备明确目标及变更，由客户端展示和按其审批机制提交；服务端不能将确认 token 或工具 annotations 视作真人批准证明。实际 Gitea 权限始终生效。

所有当前业务命令均有对应读取工具或写入 action；本地固定 Git 查询和附件上传需授权工作目录，不开放任意 shell / Git 写操作。MCP 通过显式参数或已保存的唯一上下文调用共享应用服务，缺参返回错误，不读取协议 stdin 做登录或选择。客户端工作目录默认不能假定为用户项目；Follow client workspace 通过显式 Codex／Claude 适配器或 MCP roots 为每个会话建立授权根，固定目录使用 --workdir。多根／缺失根不阻断远端业务，根变化使本地绑定和旧计划失效，详细边界见 MCP 设计第 12 节。

工具错误、部分完成、结果未知、重复提交、跨进程限制、Schema 和各客户端验收均在专门设计中明确。P6 已交付 32 工具／21 action、严格 Schema、进程计划与授权文件快照，自动验证及七版本代表性链路通过；Codex 实际转发和 Claude Code 健康检查有部分证据，四客户端完整 UI 与真实目标平台仍待实测，见 [P6 记录](p6-mcp.md)。

## 10. 错误、输出与可观测性

内部区分配置、认证、权限、仓库上下文、网络/TLS、服务端、版本能力、取消和写入结果未知等错误类别；保留必要上下文和底层原因。CLI 输出可操作的提示并返回非零状态，Git 透传保留正常 Git 退出码；MCP 返回协议允许的结构化工具错误。CLI 的稳定 envelope、逐项状态与退出码见 [CLI 契约第 6 节](cli-contract.md)，MCP 的结构化结果和工具错误见 [MCP 设计第 2 节](mcp-design.md)；通用 API 与 Git 保留原始流规则。

默认日志保持精简，调试日志可显式开启；所有级别均不得输出凭证。长输出和二进制响应应按流处理或限制大小，避免在 MCP 消息中无界返回。

## 11. 构建与分发

已确定为 macOS 和 Windows 提供预编译程序，用户无需安装 Go；同一程序包含 CLI 与 MCP 服务。建议首版构建 darwin/arm64、darwin/amd64 和 windows/amd64；windows/arm64 在具备运行验证条件后决定是否正式支持，Linux 支持仍待确认。最低操作系统版本、Git 版本及第三方依赖的平台限制需核实。

最低版本调研及支持矩阵见 [platform-support.md](platform-support.md)：Windows 已确定向下正式支持 Windows 10 22H2 amd64，同时覆盖 Windows 11，以 25H2 作为较新系统的验收基线。两个系统分别验证 Windows Terminal + Windows PowerShell 5.1，Windows 11 另验证推荐的 PowerShell 7.6 LTS；Windows 10 不强制安装 PowerShell 7。凭证、终端等依赖不得未经评估就抬高 Windows 10 下限；两个系统使用同一 windows/amd64 产物，分别完成运行验收。Git 2.43 已固定为功能基线，2.43.7 隔离样本通过；macOS 15 仍为建议基线。Go 技术下限与产品正式支持基线分别记录，后续新系统也须经过验证才能标记通过。

建议 macOS 提供 tar.gz、Windows 提供 zip，附程序版本、构建提交、使用说明、项目 MIT 许可证和 SHA-256 校验值；通过团队 Gitea 发布页分发是待确认方案。每个平台必须运行真实环境冒烟测试，交叉编译成功不足以证明可用。建议首版手动下载替换并保留配置；签名、公证、包管理器、自动更新及回滚策略待确认。第三方依赖的许可证和随产物提供的声明应分别核对。

## 14. P1 实施边界

基础实现、具体默认值与验证证据见 [p1-foundation.md](p1-foundation.md)。配置使用同目录临时文件和协作锁，按完整内容摘要检测冲突；外部编辑器不参与锁协议，检查与替换之间仍存在竞争窗口。P1 的修订标识已由 P2 长驻诊断调用消费，按完整配置内容变化隔离版本缓存。

HTTP 基础层默认总超时 30 秒、响应上限 1 MiB，调用者负责关闭响应体并处理读取错误。读取重试默认关闭，显式设置最多重试三次；写请求不自动重放。写入发送后断连或响应中途断开报告结果未知。上传下载与分页在后续阶段接入，不能把当前默认响应上限理解为首版附件大小限制。

Git 捕获默认 30 秒、每条输出流上限 1 MiB，禁止提示并响应取消；透传保留 Git 输入输出，不设查询超时。POSIX 捕获使用独立进程组清理；Windows 使用 taskkill 进程树终止及根进程回退，自行脱离进程树的后代不在强保证范围，仍需目标系统验证。当前无参数入口显示帮助，P5 才接入持续菜单；没有注册的命令不提供占位成功。


## 15. P2 实施边界

实现与实际环境见 [p2-readonly.md](p2-readonly.md)。上下文解析不读凭证，认证边界不依赖终端，仓库只读应用服务由 CLI 直接调用；MCP 原型直接调用同一上下文／认证／版本服务。每次调用重新读取配置并验证所选身份，版本缓存不代替身份与权限校验。

新增随机系统引用在配置提交成功后才接替旧引用；新 token、环境覆盖或其他来源验证失败不能误标未使用的旧凭证。退出先保存抑制，清理失败保留被抑制的记录供重试。原始 API 与协议流仍不进入业务渲染；业务脱敏登记覆盖本进程已使用的环境、自有和 helper 密钥。

七版本当前通过的是 P2 认证与仓库开发上下文，不是全部 API 兼容。Windows 10／11 的凭证、控制台输入和进程运行没有实机结果，保留为待实测；不以交叉编译代替。MCP 原型只暴露 sotea_instance_info，完整工具、写计划和 Harness 验收保留在 P6／P7。

### P5 首页资料与统一可读详情

认证服务新增最小 Profile（login、full_name、email），OpenProfile 复用原身份验证和凭证生命周期，从同次 GET /user 响应提供资料；Open 仍返回原有客户端及目标，不向业务服务引入终端依赖。菜单每轮重置资料，仅将已核对字段传入 HomeInfo；未选仓库不阻止已有实例的身份显示。

持续会话的 Home 页面使用边框卡片、常用操作排序、焦点强调与当前动作范围，宽度按完整字素计算，低矮／窄窗口减少可选资料行以保持操作可达。搜索优先精确稳定 ID，避免 version 被描述中的 Versions 遮蔽。导航按键与页面生命周期保持前述契约。

输出适配器提供统一可读字段树：列表选择摘要表格，详情递归排列标量、数组与对象；仓库识别同时要求 full_name 和仓库专用字段，避免把用户资料误当仓库。常用字段优先，其他字段稳定排序，动态字段名和内容都脱敏并清理控制符。标准分页须同时有 items、page 和 has_more，普通含 items 的详情对象不得被当成分页结果而隐藏其余字段。通用 API 的菜单 JSON 使用完整详情模式，不丢弃数组中的非摘要字段；解析预算为 2 MiB，超出或非 JSON 通过已读取前缀与剩余流拼接后原样交接。机器 JSON 与直接 API 保持现有语义。

### P5 全局页面与引导组件

MOD-11／12／13 统一复用 pageHeader、frame、choiceRows、Input 与 Notice：页面负责终端布局和稳定动作 ID，业务服务继续不读终端。名称／说明分离，兼容旧 Label 的首个分隔符；徽标使用独立 Badge，草稿标记仅由 Release 布尔状态生成。静态选择也复用名称／说明层级，直接 Git／API 流不经过页面。

正文采用 goldmark v1.8.7 的 CommonMark／GFM AST，终端渲染仅生成固定 SGR。新增此 MIT 依赖是为了处理嵌套 Markdown，避免正则解析；最低 Go 要求 1.22，不改变项目 Go 1.27.3 或平台承诺。已有 x/ansi v0.10.1 转为直接依赖用于可信样式折行，无版本升级。HTML／代码不执行、图片不下载，源文本及实体解码结果均清理控制符。MarkdownWriter 保留本地可信正文跨度及源码，随窗口宽度渲染当前组；不从远端字符串推断元数据，不影响 JSON／原始流。

账号向导编排留在 CLI，InputOptions／NoticeOptions 只承载显示与用户选择。认证服务 PreviewLogin 读取明确来源并验证 /user，不保存配置／密钥或更新旧记录的失效标记；Login 以 ExpectedAccount 绑定预览身份，保存前重新验证，沿用原子配置和密钥替换。向导在凭证预览及最终保存前核对起始配置快照；变化时不继续凭证请求。Cancel 归还原会话，成功保存保留新账号，Browse account 可续接。完整过程不新增远端写入或自动创建 token。

### P5 分组名称标签栏

结果页在正文上方用groupTabs展示可信顶层组名，不再生成Group N of M数字摘要。当前组复用章节强调色及方括号，未激活组用辅助色，关闭颜色仍有明确选择标记。宽度不足时以当前组为中心显示可容纳的连续组名，省略号表示未显示项；超长当前名称按字素安全截断，始终保留活动标记。标签只替换展示，沿用PgUp／PgDn、Tab／Shift+Tab及整组滚动／确认范围，左右键仍不切组。

### P5 简化成功结果与可信字段样式

输出适配器通过ResultTargetWriter向持续Session传递类型化目标和状态，成功只保留资源标题，其他状态继续显示；菜单依据真实退出码／结果状态简化成功页标题，不靠解析文本去除success。直接CLI／静态流仍输出原状态，JSON不变。资源标题与正文通过空行分区，顶层章节也与内容留白。

标量键通过本地field标记及FieldWriter携带可信位置，Session保存fieldSpan并与Drain后的正文一同匹配，渲染时只对键应用辅助色，不从远端空格或文本推断键值。远端控制符清理、不完整预览阻断和2MiB预算保持。Markdown与内联字段样式可组合，机器出口不接收样式元数据。

底部位置由本地命令入口／页面标题生成导航路径，菜单切换／结果展示更新，组名附加在末尾；location角色为绿色普通字重。选择器复用同一底部位置行。active-tab使用粗体、深蓝背景和留白，未激活项弱化，无竖线／方括号；NO_COLOR改为圆点标记。窄屏优先活动标签及相邻名称，不改变切组和确认语义。


### P6 实现状态（2026-11-08）

完整 MCP 已替代 P2 单诊断原型。CLI／MCP 复用 internal/app/session 的上下文、认证组合和版本服务，原始 API 请求／正文／multipart 编排提取到 internal/app/api；业务读取及原领域 Prepare／Commit 复用既有应用服务。MCP 只负责协议适配、入口授权、计划索引／去重／状态、最终消息预算和进程资源；不调用 CLI RunE 或解析终端输出。
