## 1. 目标与当前起点

按已确认的首版范围交付一个 Go 1.27.3 可执行程序，包含业务 CLI、缺参交互、无参数持续菜单、系统 Git 透传、通用 API 和本地 stdio MCP。七个指定 Gitea 版本必须支持共同功能；Windows 10 22H2 amd64 与 Windows 11 均为正式验收目标。macOS／Git 的建议基线及其他平台条件见 [platform-support.md](platform-support.md)。

当前已交付 P1 公共契约、配置、Git／helper、HTTP／TLS、脱敏输出及 Git CLI，Go 1.27.3 自动化与三平台构建通过，macOS arm64 产物冒烟通过。P2 已实现上下文／认证、仓库只读及 MCP 原型，P3 正在完成 Issue、任意方法 API 和交互选择；Windows 10／11 和候选最低平台未实测。详见 [P1 记录](p1-foundation.md)。

P0 已交付七版本固定镜像、隔离数据初始化／重置、helper／HTTP／TLS 夹具及环境记录，见 [p0-readiness.md](p0-readiness.md)；该准备结果不代表客户端业务功能已实现或平台兼容已通过。

开发按阶段和可验收交付物推进。暂不设未经估算的日历工期；完成第一条真实业务链路后，再结合人员、设备和实例准备情况估算后续工期。

| MOD-00 | 工程与应用契约；cmd/sotea、internal/app 公共部分 | 组合入口、取消传递、应用输入输出类型、稳定错误类别、测试入口和构建信息；沿用现有 Cobra 工程。 | 无 |
| MOD-01 | 配置；internal/config | 带版本 JSON、实例／账号引用、仓库绑定、退出抑制标记、原子写、并发修改检查和配置变更检测。 | MOD-00 |
| MOD-02 | Git；internal/git | 参数数组执行、仓库／worktree 发现、分支和 remote、凭证 helper 交互、透传流与退出状态、取消及子进程清理。 | MOD-00 |
| MOD-03 | 上下文；internal/context | 按契约解析目录、remote、实例、仓库和账号候选，处理显式参数冲突、SSH 到 HTTP 映射和多候选歧义。 | MOD-01、02 |

| MOD-13 | 交互；internal/tui | 共享表单、缺参选择、搜索分页、跨页勾选、写入预览确认、无参数持续菜单和终端恢复。 | MOD-07 至 11；与 MOD-12 约定交互入口 |

## 3. 依赖与执行链路

~~~mermaid
flowchart TD
    A[工程与应用契约] --> B[配置与系统 Git]
    A --> C[HTTP 传输与结果输出]
    B --> D[目标上下文]
    C --> E[认证与版本适配]
    D --> F[仓库与开发上下文]
    E --> F
    F --> G[Issue]
    F --> H[PR]
    F --> I[Release]
    G --> J[完整 CLI 与持续菜单]
    H --> J
    I --> J
    G --> K[MCP 工具]
    H --> K
    I --> K
    J --> L[完整回归与发布]
    K --> L
    T[测试实例与平台环境提前准备] -. 持续验证 .-> F
    T -. 持续验证 .-> L
~~~

组合根负责连接适配器与应用服务；HTTP 底层不依赖 CLI、菜单、MCP 或高层认证流程。上下文模块先解析目标候选，未知实例先做无凭证检测并确认来源，之后认证模块才读取和验证该实例凭证。带身份的 API 调用使用已选实例和账号，兼容层不自行切换凭证。

配置、Git、基础 HTTP 和输出可以在公共类型确定后分别推进。PR 和 Release 可在仓库服务及错误／写入模型稳定后分别推进。CLI、菜单与 MCP 共用业务服务，但分别实现各自的输入和确认机制。

## 4. 开发阶段与完成标准

每个 P 按“进入条件 → 编号任务 → 集成演示 → 验证清单 → 退出条件”执行。每张任务表使用“完成状况”列逐项记录，初始均为“未开始”；交付物是实施时要产生的结果，不表示当前已经存在。开发任务、验证用例和 DEC 决策分别追踪，不以编写本文代替实际完成。

先完成任务中明确的依赖，再接后续任务。环境准备可以与本地实现并行，但阶段实测缺失时最多标记“实现通过／待实测”；不影响其他独立任务继续，也不能据此关闭发布门槛。每个阶段的记录须关联提交、任务编号、实际环境和失败项。

#### P6.2 集成演示与验证

演示客户端以只读配置启动，发现工具并读取 Issue；再使用显式写能力配置，准备关闭指定 Issue，展示目标及变更，按客户端审批机制提交，再重复提交并查询同一结果。随后修改账号／文件／PR head，确认旧计划拒绝执行，最后断开客户端验证服务清理。

| 验证组 | 必测场景 | 通过标准 |
| --- | --- | --- |
| 模式权限 | 默认、仅 allow-write、仅 allow-raw-api、两者同时开启。 | 工具发现和实际调用双重受控；仅原始 API 开关不能开放写 action。 |
